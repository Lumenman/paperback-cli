# Журнал работ: почему лист не читается при `-d 150`

Лабораторный журнал: что мерялось, что вышло и что не вышло. Не документация — документация в README. Начат 2026-09-17.
Исходный вопрос: при `-d 150` и избыточности 1:5 лист A4 не распознаётся уверенно.

---

## 1. Что показало чтение кода

### Печать

| факт | где |
|---|---|
| Блок — 32×32 точки данных, шаг блока `NDOT+3` = 35 ячеек | `src/Printer.c` `Drawblock`, `x=(index%nx)*(NDOT+3)*dx+2*dx+border` |
| Межблочный зазор — 3 ячейки из 35, **8.6% площади листа пустует** | там же |
| В блоке: 90 байт данных + CRC16 + 32 байта RS на 127 → чинит до 16 битых байт из 128 | `Encode8((uchar *)block,block->ecc,127)` |
| Данные XOR-ятся с 0x55/0xAA по чётным/нечётным строкам — чтобы пустой блок не был белым пятном | `Drawblock` |

### Раскладка избыточности (важно, уже сделана грамотно)

`src/Printer.c`, цикл «encode and draw data, group by group»: страница делится на
`redundancy+1` непрерывных полос-«строк», j-й член каждой группы кладётся в j-ю полосу,
плюс поворот колонок на `nx/(redundancy+1)`.

Следствие: **потеря одной полосы целиком = ровно один член каждой группы = восстанавливается.**
Потеря двух полос = два члена = лист мёртв. Обрыв резкий, промежутка нет.

Отдельно: декодер полностью **позиционно-независим** — блок находится по своему полю
`result.addr`, а не по месту на листе (`Decodenextblock`: `blocklist[...].addr=result.addr & 0x0FFFFFFF`).
Значит раскладку на странице можно менять как угодно, не трогая декодер. Идея «перемешать блоки
для устойчивости» уже реализована Олегом, придумывать заново не надо.

### Привязка при декодировании

| факт | где |
|---|---|
| Глобальная модель: один угол + один шаг на весь лист | `Getxangle` / `Getyangle` |
| Подгонка делается в окне **1024×1024 в центре страницы** (`NHYST`) | `Getgridintensity`: `searchx0=centerx-NHYST/2` |
| Позиция блока — линейная экстраполяция от центра | `Decodeblock`: `x0=xpeak+xstep*(posx-blockborder)` |
| Локальный перезахват фазы внутри блока есть — `Findpeaks` по проекциям буфера | `Decodeblock` |
| Гейт: локальный шаг не должен отличаться от глобального больше чем на 1/16 (±6.25%) | `fabs(xstep-pdata->xstep)>pdata->xstep/16.0` |
| Окно поиска блока: `blockborder = max(|xangle|,|yangle|)*5+0.4` → при ровном скане **±0.4 шага блока ≈ ±14 точек** | `Preparefordecoding` |
| Измеренная точная позиция блока вычислялась и **выбрасывалась**: «Save block position for displaying purposes» | `Decodeblock`, `blockxpeak/blockypeak` |
| Обход блоков растровый, соседи не используются | `Decodenextblock` |
| Субблочная подгонка 8×8 px со сдвигом ±1 — зачаток локальной синхронизации, включается только когда блок уже не читается | `SUBDX/SUBDY`, ветка `if (answer==17)` |

**Гипотеза, с которой начинал (оказалась неверной):** глобальная подгонка в центре +
экстраполяция к краям даёт накопленный сдвиг, края листа умирают, теряются две полосы сразу
(верх и низ) — худший случай для раскладки избыточности.

## 2. Что реализовано

Ветка `quality-map-and-neighbour-resync`, коммит `712a2c5`.

### `--quality-map` (пункт 0)

`Printqualitymap` в `src/Decoder.c`, вызывается из `Finishdecoding`. Массив `qmap`
(`signed char` на позицию, `-2` = не пробовали) выделяется в `Preparefordecoding`.

Легенда: цифра = блок прочитан, значение = байт починено ECC; `+` = 10 и больше;
`#` = найден, но не прочитан; `.` = растр не найден.

Тот же массив используется для логики второго прохода — одна структура на две задачи.

### Привязка от соседей (пункт 1)

- `Predictorigin(pdata,posx,posy,&x0,&y0)` — предсказывает начало окна поиска по измеренной
  позиции соседа. Возвращает **число** годных соседей (нужно, чтобы отличить блок в гуще данных
  от позиции за краем растра).
- `orgx/orgy` — измеренная привязка каждого блока, сохраняется в `Decodeblock`
  (`x0+xpeak`, `y0+ypeak`, до пересчёта в шаг точки).
- Доверяем только соседям с сошедшимся CRC (`qmap` в диапазоне 0..16). Блок со статусом 17
  часто нечитаем именно потому, что найден не там.
- От соседа берётся **только фаза**, шаг остаётся глобальным: шаг, измеренный по одному блоку,
  слишком шумный, чтобы интегрировать его по листу.
- Второй проход по странице (`pdata->pass`), когда соседи уже известны.

### 3.1 Синтетическая деформация протяжки

`warp.py`: `srcy = y + d*h*((y/h)^2 - y/h)` — концы закреплены, локальный шаг гуляет от `1-d` до `1+d`.
Страница `-d 100`, 445 блоков.

| d | HEAD | с изменением |
|---|---|---|
| 0.003 … 0.08 | 445/445 | 445/445 |
| 0.15 | 316/445 | 316/445 |
| 0.30 | 158/445 | 158/445 |

Инструментировал счётчики отказов по четырём гейтам `Decodeblock`:

```
d=0.08  PREDICTED 565, x-nopeak=179 x-step=0 y-nopeak=40  y-step=20,  ystep=104.034
d=0.15  PREDICTED 355, x-nopeak=182 x-step=0 y-nopeak=160 y-step=120, ystep=101.381
```

Предсказание срабатывает сотни раз, но исход не меняет. При d=0.15 глобальный шаг измерен как
101.38 вместо истинных 105, а локальная деформация ±15% вышибает блоки по гейту `y-step`
(±6.25%) — предсказание позиции тут бессильно, отвергается не позиция, а шаг.

**Вывод:** ±15% деформации — это не сканер, это фотография под углом. Реальный планшетник даёт
0.1–0.5%, а окно поиска ±0.4 шага блока (±14 точек) съедает и куда больше.

### 3.2 Симулятор печати и скана

`scan.py`: растекание чернил → перекос → дрейф протяжки → размытие оптики (MTF) → дискретизация
на разрешении скана → шум. Страница: 100 КБ, `-d 150 --image-dpi 600`, скан 300 dpi
(`ratio=2`, 2 пикселя на точку), 1112 блоков.

| искажение | HEAD | с изменением |
|---|---|---|
| blur σ=0.4 px | 1112/1112 | 1112/1112 |
| blur σ=0.6 px | 1112/1112 | 1112/1112 |
| **blur σ=0.8 px** | **22/1112** | **22/1112** |
| blur σ=1.0 px | 88/1112 | 88/1112 |
| blur 0.4 + перекос 0.4° | 1112/1112 | 1112/1112 |
| blur 0.4 + дрейф ±5% | 1112/1112 | 1112/1112 |
| blur 0.4 + шум σ=12 | 1112/1112 | 1112/1112 |
| blur 0.6 + растекание 0.6 | 1112/1112 | 1112/1112 |

**Главный результат всей работы.** Геометрия (перекос, дрейф, шум, растекание) не мешает вообще.
Решает оптическое разрешение, и это **обрыв, а не склон**: между σ=0.6 и σ=0.8 пикселя
лист падает с 1112 блоков до 22. При 2 пикселях на точку запаса по размытию нет никакого.

Немонотонность 22 → 88 при σ=1.0 — это переключение `maxdotsize` на другой размер усреднения,
обе точки одинаково мертвы.

### 3.3 Карта качества различает причины

Замыленный скан (σ=0.8):

```
..+######+#####################+#..
..###############################..
```

Стёртая полоса на листе:

```
..0000000000000000000000000000000..
...................................
...................................
..0000000000000000000000000000000..
```

`#` по всему листу — оптика. `.` полосой — потерянная привязка. Работает как задумано.

## 4. Три версии пункта 1 и почему менялись

**v1 — предсказание вместо глобальной сетки всегда.**
Срабатывало 355 раз из ~565, но результат либо тот же, либо **на 1–2 блока хуже**:
930→929, 846→844, 1092→1090. Причина: фаза, взятая от одного соседа, шумнее подгонки,
усреднённой по всему листу. Забраковано.

**v2 — предсказание как резервный путь.**
Глобальная сетка первой; сосед спрашивается только для блока, который провалился
(`answer<0 || answer>=17`). Регрессий нет, при σ=1.0 стало 90 вместо 88.
Цена: чистая страница 1393 мс против 1096 у HEAD (+27%) — за счёт позиций **за краем растра**,
где `answer=-1` и у позиции есть один сосед, так что повторная попытка запускалась впустую.

**v3 (текущая) — плюс требование двух расшифрованных соседей.**
Позиция за краем растра имеет одного соседа, блок в гуще данных — два и больше.
Накладные расходы на чистой странице исчезли. Вместе с ними исчез и выигрыш в 2 блока.

Тайминги (страница 1112 блоков):

| | HEAD | v2 | v3 |
|---|---|---|---|
| чистая страница | 958 мс | 1393 мс | 888 мс |
| массовые отказы | 2273 мс | 5822 мс | 4296 мс |

Удвоение времени на сбойной странице — ровно там, где вторая попытка и нужна.

## 5. Честный итог

1. **Пункт 1 не дал измеримого выигрыша ни в одном смоделированном режиме.** Реализован
   корректно, срабатывает, на здоровой странице ничего не стоит, хуже нигде не делает.
   Может помочь на реальной мятой бумаге или на снимке камерой — локальную коробку бумаги
   симулятор не моделирует. Но доказательств пользы у меня нет.
2. **Исходный диагноз («срыв глобальной привязки у краёв») был неверен.** В `Decodeblock`
   уже есть локальный перезахват фазы в окне ±14 точек — на порядок больше, чем даёт
   любой планшетник. Геометрия не узкое место.
3. **Узкое место — оптика.** При `-d 150` и скане 300 dpi на точку приходится 2 пикселя,
   и MTF сканера σ≈0.8 px убивает страницу целиком. Это объясняет и то, почему `-r 5` не
   помогает: отказы не случайные и не локальные, а массовые, ECC в такой ситуации бессилен.
4. **Полезен оказался пункт 0.** Карта — единственное, что отличает «растр потерян» от
   «точки нечитаемы», не гадая.

## 6. Что делать дальше

### Сначала — бесплатное

```
paperback-cli --decode --quality-map -i scan.bmp -o out.bin
```

- сплошные `#` → оптика: скан 600 dpi (4 px на точку, включается усреднение 4×4 в
  `Preparefordecoding`: `maxdotsize=4`), печать `--image-dpi 600` вместо умолчания
  `3*dpi=450`, которое лазерник 600 dpi пересемплирует с коэффициентом 1.333;
  в драйвере снять автоуровни, резкость, descreen;
- `.` полосами/по краям → геометрия, тогда v3 начнёт работать;
- много `5`…`9` и `+` → запас ECC тает, лист на грани.

Проверить `-s`: 70 для струйника много (растекание), 60 лучше; для лазера 80.

### Потом — по возрастанию цены

| шаг | цена ёмкости | что чинит |
|---|---|---|
| Клок-гребёнка в межблочном зазоре (3 пустые ячейки уже оплачены) | 0 | абсолютную привязку каждого блока |
| RS поперёк всех блоков страницы вместо XOR 1:N | 0 | обрыв «две полосы = ноль» → плавную деградацию |
| Полосная топология Softstrip (клок по краям полосы 190 мм) | **+8%** (зазор 8.6% → клок 0.2%) | построчную синхронизацию |

Про полосную топологию: построчный клок внутри блока 32×32 при `-d 150` — это клок на
дистанции 5.9 мм, там деформаций нет, платить не за что. Он начинает работать только
если полоса во всю ширину поля.

## 8. 18.09: измеренная оптика вместо угаданной, и дырка в декодере, которую она нашла

Рядом положены исходники `paper-sound` — печать звука гуляющей линией. Формат
другой, интересна метрология: там та же пара «лазерник + планшетник» и лист,
который печатает известную величину и меряет её обратно.

### 8.1 Что взято: PSF, померенный на бумаге

`paper-sound/grating.py` печатает полосу из девяти решёток с известными
периодами и читает контраст каждой — это и есть MTF пары принтер+сканер.
Результат (`LAB.ru.md` §24.6): подгонка `A*exp(-2pi^2 s^2 / lam^2)` даёт
**A = 0.919, s = 1.077 px при 600 dpi**, причём одной гауссианы мало — острое
ядро s ≈ 1.09 плюс широкий ореол, плоский уже к периоду 20 px и стоящий 8%
контраста. Рассеяние тонера и блик стекла.

`scan.py` получил режим `mtf=1`, который ставит вместо угаданного `blur` эти
две гауссианы (`MTF_SIGMA`, `MTF_HALO`). `mtf=` — множитель на сигму, то есть
«во сколько раз сканер хуже померенного». Проверка — `experiments/mtf_check.py`:
девять решёток через симулятор, контраст против непорченого, допуск 0.06.

| период px | модель | бумага |
|---|---|---|
| 2.9 | 0.056 | 0.053 |
| 4.9 | 0.350 | 0.400 |
| 9.9 | 0.731 | 0.690 |
| 19.7 | 0.866 | 0.815 |
| 38.7 | 0.921 | 0.956 |

**Первый же вывод отменяет §3.2.** Угаданный blur=0.8 px на скане 300 dpi — это
1.6 px при 600 dpi, то есть **в полтора раза хуже настоящего сканера**. На
измеренном PSF лист `-d 150` читается целиком и на скане 600 dpi, и на 300 dpi.
Оптика не была стеной, стена стояла на полтора сигмы дальше.

### 8.2 Где настоящий предел (измеренный PSF, множитель сигмы)

Страница 40 КБ, 445 блоков, `--image-dpi 600`. Плотность `-d` округляется до
целых пикселей на ячейку: 150 → 4 px, 200 → 3 px, 300 → 2 px при 600 dpi.

| лист | px на точку в скане | целиком читается до |
|---|---|---|
| `-d 150`, скан 600 dpi | 4 | > 2.0x (не доведено) |
| `-d 150`, скан 300 dpi | 2 | 2.0x, при 2.25x — 413/445 |
| `-d 200`, скан 600 dpi | 3 | 1.75x |
| `-d 200`, скан 300 dpi | 1.5 | не читается вовсе |
| `-d 300`, скан 600 dpi | 2 | 1.0x — запаса нет |

Два пикселя на точку работают, но ровно на померенном сканере; полтора не
работают никогда — это Найквист, а не оптика. Практический ответ на исходный
вопрос: **`-d 150` со сканом 600 dpi имеет двукратный запас по размытию**, и
если лист не читается, виновата не плотность.

### 8.3 Что PSF нашёл в декодере: провал между двумя пикселями

Сначала цифры выглядели как ерунда — немонотонность, та же, что в §3.2
(22 → 88), только резче:

| множитель сигмы, скан 300 dpi | HEAD |
|---|---|
| 1.0 | 445/445 |
| 1.5 | **6/445** |
| 1.75 | **не найден заголовок** |
| 2.0 | 445/445 |

Более размытый лист читается, менее размытый — нет. Размытие так не работает,
значит виноват декодер. Карта качества: при 1.5 весь лист в `#` — блоки найдены
и не прочитаны.

Проверено по порядку:

1. **Не таблица `factor`.** `Recognizebits` вычитает соседей как
   `factor*себя - 4 соседа`, `factor` из {1000, 32, 16} — три жёстких значения,
   два из них на октаву друг от друга. Гипотеза «лист попал между ними»
   красивая и **неверная**: с таблицей {1000, 48, 32, 24, 16, 12} ничего не
   изменилось.
2. **Не оценка резкости и не сетка.** Логировано: `cmin/cmax`, `contrast`,
   `sharpfactor`, `xstep/ystep` — всё меняется гладко и монотонно, шаг измерен
   как 69.885 против истинных 70.0 на всех листах.
3. **Резкость — симптом.** Через временной `PB_SHARP` на листе 1.5x:
   `sharp=0` → 445/445, автоматический `sharp=0.76` → 6/445. Но `sharp=0`
   ломает лист 2.0x (295/445), а `sharp=0.3` ломает его совсем (16/445).
   Ни одного значения, годного для обоих, — значит не в силе фильтра дело.
4. **Фаза сетки.** `Decodeblock` собирает **девять** сеток — со сдвигами ±1 px
   во всех направлениях, — а `Recognizebits` зовёт ровно одну, `g[4]`,
   несдвинутую. Остальные восемь 1.20 использует только для пересборки блока по
   субблокам с максимальной дисперсией. При двух пикселях на точку ошибка фазы
   в один пиксель — это половина точки, и все 32x32 отсчёта берутся не оттуда.

### 8.4 Исправление: три строки

`Decodeblock` перебирает уже собранные девять сеток, пока блок не прочитан:
несдвинутая первая, затем четыре по осям, затем диагонали. Учёт `M_BEST` не
дублируется — цикл обошёл ту же ветку, что и раньше.

| множитель сигмы, `-d 150` скан 300 dpi | HEAD | с циклом |
|---|---|---|
| 1.0 | 445/445 | 445/445 |
| 1.25 | 445/445 | 445/445 |
| **1.5** | **6/445** | **445/445** |
| **1.75** | **мёртв** | **445/445** |
| 2.0 | 445/445 | 445/445 |
| 2.25 | 411/445 | 413/445 |
| 2.5 | мёртв | мёртв |

Кривая стала монотонной: провала между двумя пикселями больше нет. На остальных
двенадцати клетках матрицы (`-d` 150/200/300 x скан 600/300 x сигма 1.0/1.5/2.0)
результат совпал с HEAD до блока — регрессий нет.

Проверено отдельно: восстановленный файл совпадает с исходным по SHA-256
(`--expect`), а страница чистого шума по-прежнему не отдаёт ни одного блока —
перебор сдвигов не выдумывает данных, за ним всё те же RS и CRC16.
`make test` и `test_core` проходят.

Цена:

| | HEAD | с циклом |
|---|---|---|
| чистая страница | 2970 мс | 2443 мс |
| безнадёжная страница | 3024 мс | 7468 мс |

Чистая страница не платит (первой пробуется та же сетка, что и раньше; разница
в пределах шума стенда). Безнадёжная платит 2.5x: восемь лишних `Recognizebits`
на каждый непрочитанный блок, на каждом размере точки. Это та страница, которую
всё равно пересканируют.

### 8.5 Что ещё оттуда стоит взять — по убыванию пользы

1. **Лист печатает собственную линейку** (`LAB` §23.11) — **сделано, §9**. Там штрих печатается
   шириной 4 px, и если скан отдаёт 3.2 px, это физически невозможно: краска
   только растекается. Значит сканер «выпрямляет» края — резкость или
   собственный контраст, — и выбрасывает ровно те пиксели частичного покрытия,
   в которых живёт субпиксельная позиция. Автоуровни и белую точку так видно
   **из самого изображения, без эталона**. У нас точка печатается известной
   ширины (`-s 70` от шага, при `-d 150` и 600 dpi это 2.8 px) — приём годится
   один к одному и ложится рядом с `--quality-map`: карта говорит
   «не прочитано», линейка — «потому что сканер порезал края».
2. **Порядковая статистика вместо порога** (`axis.py`, §23.1) — **померено и отклонено, §10**. Монотонная
   тоновая кривая переставляет уровни серого, но не может их переупорядочить,
   поэтому ранг переживает гамму, автоуровни и экспозицию, а значение — нет.
   У нас порог считается из `cmin/cmax` по 3% хвостам гистограммы **центрального
   окна 1024x1024** — это значения, а не ранги. В `paper-sound` идея померена
   и **отклонена**, но там оценивалась субпиксельная позиция по одному ряду;
   у нас нужно бинарное решение по 1024 точкам блока, и запас совсем другой.
3. **Профиль, просуммированный вдоль наклона** (`read_tracks.col_profile`,
   §19) — **уже был в 1.20; нашлось другое, §11**. Сдвиг каждой строки на -lean*y индексной арифметикой перед
   суммированием, ни одного пересчитанного пикселя, двадцать строк кода — и
   потолок по перекосу уехал с 0.33° до 16°, то есть вышел из ридера и упёрся
   в стекло. У нас `Getxangle`/`Getyangle` ищут угол честно, но в окне
   `NHYST` 1024x1024 в центре листа; лист мерится своей серединой, а не целиком.
   Дёшево, но не нужно, пока §3.2 показывает, что геометрия не жмёт.
4. **Не брать: решётка вместо одной точки** (§24.6, +8 dB). Выигрыш там из
   метрологии — «краёв x ход края в квадрате», — и он про оценку *позиции*
   штриха. У нас носитель бинарный, позиция ничего не несёт, переносить нечего.

### 8.6 Воспроизведение

```sh

# скан 600 dpi и 300 dpi с измеренным PSF

python experiments/scan.py e150.bmp s.bmp ratio=2 blur=0 mtf=1.5
```

## 9. 18.09: линейка — ширина точки в скане

Пункт 1 из §8.5. Точка печатается известной долей ячейки, а краска на бумаге
только растекается: пройдя принтер, бумагу и стекло, точка может вернуться
шире, но не уже. Значит лист несёт собственную линейку, и по ней видно
единственное повреждение, которое больше нигде в изображении следа не
оставляет — сканер, «выпрямляющий» края.

### 9.1 Чего в нашем формате нет: изолированной точки в смысле `paper-sound`

Там штрих шириной 4 px стоит в полосе шириной 38.7 — вокруг него бумага.
У нас точка занимает `-s` процентов ячейки, по умолчанию 70, и при `-d 150`
с `--image-dpi 600` это **3 px из 4**: между двумя соседними чёрными точками
остаётся 1 пиксель бумаги. Первая версия искала точку, вокруг которой бумага,
и не нашла ни одной.

Нашлась она там, где и должна: изолирована не точка, а **ячейка**. Белая ячейка
— это 4 px бумаги целиком, потому что точка в ней не напечатана. Поэтому
критерий — «чёрная ячейка, у которой все четыре соседние ячейки светлее на
(cmax−cmin)/4», и такие на случайных данных составляют около 3% ячеек.

### 9.2 Бины не работают, интерполяция работает

Профиль набирается с шагом в 1/24 ячейки. Первая версия складывала в бины по
тому, куда попали целые пиксели, — и бины остались пустыми. Причина ровно
обратна той, на которой стоит `grating.py`: там периоды решёток **нарочно**
не целые, чтобы штрихи прошли все субпиксельные фазы. У нас лист напечатан и
отсканирован на одном и том же dpi, шаг сетки — почти ровно целое число
пикселей (69.885 на 35 ячеек, то есть 1.9967 px на точку), и точки со своей
фазы не сходят. Ждать, что они разбредутся по бинам, нечего.

Поэтому профиль **берётся в точках**, а не раскладывается по ним: значение
буфера в дробной позиции, билинейно по четырём пикселям вокруг. Тогда каждый
бин кормится каждой точкой, и разрешение профиля не зависит от того, куда сел
растр. Билинейность по обеим осям, а не ближайшая строка: при точке в 3 px срез
на полпикселя мимо центра читается заметно уже.

### 9.3 Что получилось

Ширина на половине собственной глубины, в процентах ячейки, по обеим осям в
один профиль. Меряется по **неразмытому** буферу блока (`pdata->unsharp`) —
тому, что был до unsharp-маски декодера, — по первым 400 изолированным точкам,
то есть примерно по тринадцати блокам.

Цифровой лист, бумаги не видевший:

| лист | напечатано | линейка |
|---|---|---|
| `-d 100`, `--image-dpi 300`, `-s 70` | 2 px из 3 = 67% | **67%** |
| `-d 150`, `--image-dpi 600`, `-s 70` | 3 px из 4 = 75% | **75%** |
| `-d 100`, `-s 50` | 2 px из 3 = 67% | **67%** |
| `-d 100`, `-s 100` | 3 px из 3 = 100% | **100%** |

Точно, включая округление принтера до целых пикселей — то самое, которого
декодер знать не может, потому что не знает `--image-dpi`. Поэтому порог
предупреждения широкий: **0.9 от номинала `-s`**, а не 0.95, как в
`paper-sound`, где печатная ширина известна ровно.

Через измеренный PSF (§8.1) и через порчу тоновой кривой:

| скан | линейка | предупреждение |
|---|---|---|
| измеренный PSF, 600 dpi | 84% | — |
| измеренный PSF, 300 dpi (2 px на точку) | 102% | — |
| он же, линейное растяжение уровней | 84% | — |
| он же, белая точка 10% | 77% | — |
| он же, белая точка 20% | 66% | **да** |
| он же, S-кривая ×1 | 72% | — |
| он же, S-кривая ×2 | 60% | **да** |
| он же, S-кривая ×3 | 49% | **да** |

Размытие уводит ширину **вверх** (75 → 84 на 600 dpi, до 102 на 300 dpi, где
FWHM определяется уже блюром, а не печатной точкой) — правило «только шире»
держится, и линейка никогда не обвиняет зря. Линейное растяжение уровней не
двигает ничего: половина глубины берётся от собственных минимума и максимума
профиля, и к линейному отображению она инвариантна. Видна только **кривизна** —
это ровно то, что §23.11 проверяет своим `3x − 1.0`.

### 9.4 Где печатается

Строка с измерением — под `--quality-map`, рядом с картой блоков: карта
говорит «не прочитано», линейка — «потому что сканер порезал края».
Предупреждение печатается **всегда**, без флага: молчащий испорченный скан —
как раз тот отказ, который оно ловит.

```
Dot measures 84% of the cell against 70% printed (-s, which the printer rounds
to whole pixels); 400 dots
```

Проверка в `test_cli.py`: лист `-s 50` при `--dpi 100` обязан прочитаться как
67% (арифметика принтера, без всякого скана); он же, представленный декодеру
как `-s 100`, обязан вызвать предупреждение; лист `-s 100` — прочитаться как
100% и промолчать. Ни numpy, ни картинок — только сам бинарник.

Стоимость: 400 точек на страницу, примерно тринадцать блоков, на чистой
странице в шуме стенда (2722 мс против 3021 у HEAD).

### 9.5 Что линейка не ловит

- **Линейные правки** — яркость, контраст «ползунком», растяжение уровней.
  Они не двигают половину глубины и данным не вредят.
- **2 px на точку.** Там ширина определяется размытием (102%), и запаса на
  «уже, чем напечатано» почти нет — предупреждение сработает, но поздно.
  Линейка полезна там, где полезно и всё остальное: 4 px на точку.
- **Чужой `-s`.** Если лист печатался не с умолчанием, декодеру надо это
  сказать (`-s` работает и при `--decode`), иначе линейка мерит против чужого
  номинала. Сообщение об этом говорит прямо.

## 10. 18.09: порядковая статистика вместо порога — сделано, померено, отклонено

Пункт 2 из §8.5. Результат отрицательный, код удалён; здесь то, что от него
осталось полезного.

### 10.1 Сначала — §8.5 был неточен

«Порог считается из `cmin/cmax` по 3% хвостам гистограммы — это значения, а не
ранги» неверно: 3% хвост гистограммы **и есть** ранг. Претензия должна была
звучать иначе — `cmin/cmax` берутся из **центрального окна 1024×1024** и
применяются ко всему листу.

Настоящий порог живёт не там. В `Recognizebits` он такой:

```
c = grid[j][i]*factor - (четыре соседа)
limit = (сумма c по 1024 ячейкам)/1024 + lcorr*factor
бит = (c < limit)
```

То есть **среднее** по блоку плюс один из трёх сдвигов. Вот это — значение.

### 10.2 Что построено

Порог по рангу: копия `grid1`, `qsort`, `limit = (p[256] + p[768])/2` — середина
между квартилями собственных 1024 ячеек блока. Квартили, а не медиана: доля
чёрных ячеек лишь примерно половина, и медиана при перекосе садится внутрь
одного из облаков, а середина между квартилями остаётся в зазоре.

Добавлено тремя комбинациями (по одной на каждый `factor`) в тот же перебор,
что уже отбирается по CRC, плюс два временных ключа `PB_NORANK` / `PB_ONLYRANK`,
чтобы мерить три режима одним бинарником: только среднее, только ранг, оба.

### 10.3 Померено: ничего, нигде

28 случаев — гамма 0.3…4.0, S-кривые, белая точка, шум, градиент освещения
поперёк листа, тень от корешка до 0.15 яркости, сильное растекание чернил,
и всё это на 4 px и на 2 px на точку, при множителе PSF 1.0, 2.0 и 2.25.

| случай | среднее | ранг | оба |
|---|---|---|---|
| PSF 1.0, 300 dpi | 445/445 | 445/445 | 445/445 |
| PSF 2.25, 300 dpi | 413/445 | 411/445 | 413/445 |
| + гамма 0.4 | 409/445 | 409/445 | 409/445 |
| + гамма 3.0 | 415/445 | 415/445 | 415/445 |
| + градиент до 0.45 | 404/445 | 404/445 | 404/445 |
| тень до 0.15, 600 dpi | 441/445 | 441/445 | 441/445 |
| тень 0.15 + гамма 0.5 | 384/445 | 384/445 | 384/445 |
| растекание 0.9 | 445/445 | 445/445 | 445/445 |

Совпадение до блока во всех случаях кроме одного, где ранг **на два блока
хуже**. Обе колонки одинаково реагируют на всё, что портит лист, — значит
порог в этих отказах не участвует вовсе.

### 10.4 Почему — механизм, а не невезение

Данные XOR-ятся с 0x55/0xAA по чётным и нечётным строкам (`Drawblock`). Это
отбеливание: любой блок, включая блок из одних нулей, выходит на бумагу
примерно **половина на половину**, разброс биномиальный, ±16 точек из 1024.

При гарантированном делении 50/50 среднее по 1024 ячейкам — несмещённая оценка
той самой точки, где кончается одно облако и начинается другое. То есть среднее
здесь **не значение, а оценка ранга**, и оценка по тысяче отсчётов вместо двух.
Порядковая статистика оценивает ту же величину с дисперсией во много раз выше —
отсюда и те два потерянных блока.

Довод из `paper-sound` («монотонная кривая переставляет значения, но не может их
переупорядочить») верен и здесь. Просто Олег уже заплатил за ранг заранее — маской
0x55/0xAA, — и второй раз платить не за что. В `paper-sound` отбеливания нет и
быть не может: там носитель — позиция штриха, а не бит.

### 10.5 Заодно выяснилось, где на самом деле ломается тень

Лист «тень до 0.15 + гамма 0.5» теряет 61 блок. Карта качества:

```
.........000000000000000000000000..
.........000000000000000000000000..
```

Потерянные блоки — **точки, а не решётки**: растр в тени не найден вовсе.
Это `Getxangle`/`Findpeaks`, а не порог; никакое правило выбора порога тут
помочь не могло, потому что до порога дело не доходит. Карта качества опять
отработала как задумано — сказала, куда не надо смотреть.

### 10.6 Итог

Код удалён. Осталось это описание и набор искажённых листов, на которых теперь
меряется всё остальное.

Открытым остаётся другое: `cmin/cmax` действительно сняты с центрального окна и
применяются ко всему листу — это и порог обрезки в unsharp-маске
(`max(cmin,min(...,cmax))`), и оценка резкости, и подстановка `cmax` за краем
блока. На листе с тенью они заведомо неверны для тёмного края. Но пока такой
лист теряет блоки **до** этого места, чинить надо поиск растра, а не уровни.

## 11. 18.09: наклонный профиль — он уже есть, а не хватало не наклона, а охвата

Пункт 3 из §8.5. Вышло не то, что предполагалось, и нашлось другое.

### 11.1 Наклонный профиль в 1.20 уже реализован

`Getxangle` перебирает углы `a` и для каждого набирает профиль колонок со
сдвигом каждой строки:

```c
x = x0 + (y0+j)*a/NHYST;               // Affine transformation
```

Это построчная индексная арифметика, ни один пиксель не пересчитывается — то
есть буквально `read_tracks.col_profile(ink, lean)` из §19 звукового журнала.
Переносить нечего: Олег сделал это в 2007 году.

Диапазон: `a` от −(NHYST/20)·2 до +(NHYST/20)·2, то есть ±0.1 рад = **±5.7°**,
шагом 2/1024 = 0.0020 рад = 0.11°. А физический предел — стекло: A4 на A4
перестаёт влезать около 1.2° (`LAB` §18.4). Расширять тоже нечего.

### 11.2 Померено: угол и так измеряется верно

Лист `-d 150`, измеренный PSF, `skew` в симуляторе:

| перекос | должен быть, рад | измерено | прочитано |
|---|---|---|---|
| 0° | 0 | 0.00000 | 445/445 |
| 0.1° | 0.00175 | 0.00195 | 445/445 |
| 0.2° | 0.00349 | 0.00391 | 445/445 |
| 0.5° | 0.00873 | 0.00781 | 445/445 |
| 1.0° | 0.01745 | 0.01758 | 445/445 |
| 2.0° | 0.03491 | 0.03516 | 445/445 |

Всё в пределах собственной дискретности 0.0020 рад. То же на скане 300 dpi и
при множителе PSF 2.0–2.25: угол правильный, шаг правильный (140.00 против
истинных 140), теряются только те блоки, где точки сами по себе нечитаемы.
Наклон — не узкое место, §3.2 опять прав.

### 11.3 Зато нашлось настоящее: вся привязка живёт в одном окне 1024×1024

`Getgridintensity` ставит окно в центр растра, и из него берётся **всё**:
уровни чернил и бумаги, оценка резкости, и — через `searchx0..searchy1` —
профиль, по которому ищутся угол и шаг.

Достаточно, чтобы это окно оказалось пустым. 1024 пикселя при 600 dpi — это
**4.3 см**: наклейка, кофейное кольцо, белый залом, стикер с подписью. Тогда
`cmax-cmin<1`, и лист отвергается целиком:

```
No image
No readable file header found
```

Проверено: вырезать белым ровно окно (с полем 60 px) — и **HEAD теряет лист
целиком** при том, что остальные 95% листа в порядке.

### 11.4 Исправление в две части

**Профиль кормится всей высотой растра.** `h[]` шириной 1024 колонки, и это
остаётся; но строки, которые в него складываются, берутся от `gridymin` до
`gridymax`, а не из того же квадрата. Тех же 256 строк (`ystep=dy/256`), только
размазанных по листу, — цена ровно та же. Два следствия: неверный угол теперь
смазывает гребёнку по всей странице, а не по тысяче строк (1.20 не случайно
пришлось добавлять здесь смещение в пользу нуля — «weights for a=0 and ±2 are
the same»), и пустое пятно **разбавляет** гребёнку вместо того, чтобы быть всей
гребёнкой. Симметрично для `Getyangle` по ширине.

**Уровни: окно, а лист — если окно непредставительно.** `Getlevels` вынесена
отдельной функцией, вызывается дважды: по окну и по растру со шагом строк
(1024 строки, цена не растёт с размером листа). Если контраст окна **меньше
половины** контраста листа, берутся уровни листа.

Сравнение с листом, а не с константой: на здоровой странице оба совпадают, и
тогда всё остаётся ровно как в 1.20.

### 11.5 Почему уровни переключаются, а не берутся с листа всегда

Потому что всегда — хуже. `cmin/cmax` — это 3% перцентили, то есть они зависят
от того, сколько чернил в измеряемой области; на растре доля чернил другая, чем
в окне, и разность `cmax−cmin` уезжает (149/244 → 137/242 на одном из листов,
размах +10%). А `cmax−cmin` стоит в числителе оценки резкости
`sharpfactor=(cmax−cmin)/(2·contrast)−1` — той самой ручки, про которую §8.3
показала, что она на ножевом краю.

Померено, «всегда с растра»:

| лист | окно (1.20) | всегда растр |
|---|---|---|
| PSF 2.0, 300 dpi | 445/445 | **444/445** |
| PSF 2.25, 300 dpi | 413/445 | **409/445** |
| тёмная клякса, 300 dpi | 445/445 | **439/445** |
| тень 0.15 + гамма 0.5 | 384/445 | **414/445** |

То есть широкие уровни реально помогают листу с тенью (+30 блоков) и реально
мешают размытому. Переключение сохраняет все старые цифры и всё равно спасает
мёртвые листы; блендить пришлось бы с перенастройкой резкости, и это отмечено
в коде как `ponytail:`.

### 11.6 Результат

| лист (пятно ровно в окне) | HEAD | с изменением |
|---|---|---|
| 600 dpi, пятно 1144×1144 | **No image** | 389/445 |
| 600 dpi, пятно 1544×1544 | **No image** | 334/445 |
| 300 dpi, пятно 1144×1144 | **No image** | 201/445 |

Последний честно мёртв: 1544 px из 3508 — это 44% высоты листа, и стёрта в том

Регрессий нет: 68 листов набора (гамма, S-кривые, белая точка, шум, градиент,

### 11.7 Что осталось

Профиль по-прежнему шириной 1024 пикселя и стоит в центре — окно можно
разбавить пустотой, но нельзя сдвинуть. Пятно, накрывающее центральные 1024

окна, то есть перебором позиций, — но такого повреждения (вертикальная полоса
шириной 4 см через весь лист) у меня в наборе нет, и придумывать его, чтобы
оправдать код, — ровно то, чего не надо делать.

## 12. 18.09: три листа одного файла, один принятый неверный блок и 16 бит под ним

Пришло с бумаги: один файл напечатан трижды (`-s 55`, `70`, `85`), три скана
декодируются вместе, программа говорит «910/910, 0 missing, 95 repaired» —
и тут же «File checksum mismatch», файла нет.

### 12.1 Сначала — эксперимент с `-s` был не тем, чем казался

Точка рисуется целым числом пикселей внутри целой ячейки. При `-d 150` и
`--image-dpi` по умолчанию (450) ячейка — 3 px:

| `-s` | нарисовано |
|---|---|
| 55 | 2 px из 3 = 67% |
| 70 | 2 px из 3 = 67% |
| 85 | 3 px из 3 = 100% |
| 100 | 3 px из 3 = 100% |

Битмапы `-s 55` и `-s 70` **побайтово совпадают**; `-s 85` и `-s 100` — тоже.
То есть три листа — это два варианта, а не три. Линейка на сканах подтвердила
независимо: 55 и 70 померены в одни и те же 91%, 85 — в 117%.

| лист | линейка | прочитано | `+` (на пределе ECC) | `#` |
|---|---|---|---|---|
| 55 | 91% | 745/910 | 728 | 269 |
| 70 | 91% | 733/910 | 745 | 283 |
| 85 | **117%** | **890/910** | 826 | 112 |

Крупная точка выигрывает вчистую, и 117% — то есть точки смыкаются, зазора нет
вовсе. Симуляция §«дот-сайз» обещала обратное; она была неправа потому, что её
«крупная точка» — резкая заливка ячейки, а на бумаге это 3-пиксельная точка,
расплывшаяся за её край. Листу не хватает контраста (размах чернила-бумага 135
уровней из ~190), а не зазора, и лишние чернила дают именно контраст.

Энкодер теперь печатает, что нарисовал: `cell 3x3 px, dot 2x2 px = 67% of the
cell`. Без этой строки такой опыт ставится вслепую.

### 12.2 Потом — настоящая находка: принят неверный блок

Сверка по сборкам на тех же трёх сканах (эталон — вывод сборки до
экспериментов):

| сборка | repaired | результат |
|---|---|---|
| HEAD до работ | 90 | файл верный |
| + перебор девяти сеток | 93 | **File checksum mismatch**, файла нет |
| + привязка по листу | 93 | файл верный (везение) |

`--force` на средней сборке даёт файл, отличающийся от верного ровно в **одном
блоке из 910** — блок 182, 49 из 90 байт. Значит блок был принят с неверными
данными, а CRC16 файла это поймал. Это правильная работа последней линии
обороны, но вопрос — как блок прошёл свою собственную проверку.

### 12.3 Механизм: путь со стираниями тратит всю избыточность

В `Recognizebits` после неудачи обычного декодирования есть повтор, которого
**в 1.20 нет** (там только `Decode8(result,NULL,0,127)`; добавлено в этом порту
до моих работ): 32 наименее надёжных байта объявляются стираниями, и RS решает
относительно них.

Рид-Соломон здесь исправляет 16 байт неизвестной позиции или 32 известной. Объявив
32 стирания, мы расходуем **всю** избыточность: любые оставшиеся 95 байт дают
формально корректное кодовое слово. Никакой проверки, кроме **CRC16**, не
остаётся — 1 попытка из 65536 проходит с выдуманными данными. И адрес тут не
спасает: он берётся из того же блока, поэтому всегда правдоподобен и
`Addblock` его пропускает.

Значит цена — число попыток. Перебор девяти сеток умножил его **в девять раз**:
на трёх сканах это ~180 тысяч попыток со стираниями против ~20 тысяч, то есть
ожидание ложных приёмов выросло с 0.3 до ~2.7. Наблюдался один.

### 12.4 Исправление: стирания только на несдвинутой сетке

Сдвиги нужны, чтобы найти **фазу**; с правильной фазой блок читается обычным
путём, где RS остаётся полноценной проверкой. Поэтому `Recognizebits` получила
параметр `erasures`, и восемь сдвинутых сеток идут без стираний — ровно та
экспозиция, что была в HEAD.

Выигрыш сдвигов уцелел полностью, и это не компромисс, а улучшение:

| лист | без гейта | с гейтом |
|---|---|---|
| 02.bmp | 107 пропусков | **105** |
| 85.bmp | 20 | 20 |
| 70.bmp | 177 | 176 |
| 55.bmp | 165 | 165 |
| три скана вместе | 93 repaired, один блок неверен | 92 repaired, **файл верный** |
| синтетика, множитель PSF 1.5 и 1.75 | 445/445 | 445/445 |

Почему стало **лучше**, а не так же: ложно принятый блок не только портит
данные, он занимает слот. `Addblock` проверяет `datavalid[i]!=1`, поэтому
правильный блок, пришедший потом с другого скана, отбрасывается. Одна выдумка
стоит двух блоков.

### 12.5 Что осталось открытым

1. **Путь со стираниями сам по себе — ставка 1:65536**, и на несдвинутой сетке
   он по-прежнему пробуется на каждом размере точки и каждой из 12 комбинаций
   порога. На плохом листе это ~7 тысяч попыток, то есть ожидание 0.1 ложного
   приёма за прогон. Это поведение HEAD, и я его не менял, но теперь известно,
   чем оно оплачено.
2. **CRC16 файла — тоже 16 бит.** Здесь он сработал, но один раз из 65536 не
   сработает, и тогда испорченный файл сохранится молча. Единственное
   доказательство — `--expect` с SHA-256; на листе он печатается в подвале при
   `--header`.
3. **Карта качества не отличает блок, принятый по стираниям.** `answer`
   зажимается в 16, так что такой блок выглядит как обычный «плохой, но
   прочитанный». Отдельный символ для него сказал бы «этот блок держится на 16
   битах» — стоит сделать, это диагностика, а не поведение.

`75.bmp` прочитан **целиком и без единой починки ECC**, и его SHA-256 совпадает

Там сказано «крупная точка выигрывает вчистую». Пять точек говорят иначе:

бумаги. При 600 dpi печать идёт пиксель в пиксель.

По измеренной ширине оптимум виден и он **чуть ниже 100%**:

| линейка | прочитано |
|---|---|
| 91% | 733, 745 |
| **96%** | **910, 0 починок** |
| 117% | 890 |
| 122% | 908 |

Мало чернил — не хватает контраста; слишком много — точки смыкаются и
модуляция гибнет. 96% попадает между. Прежний мой совет «целиться в 75–85%
измеренной ширины» неверен: 91% уже слишком мало.

Оговорка, которую надо держать: у `-s 85` при 450 dpi и `-s 100` при 600 dpi
физическая точка **одна и та же** (3/450″ = 4/600″ = 1/150″), а линейка дала
117% и 122%, блоков 890 и 908. Значит разброс от отпечатка к отпечатку у этого
принтера заметен, и одиночные листы нельзя сравнивать до последнего блока.

### 13.2 Что из этого следует для рекомендаций

1. **`--image-dpi` = разрешение принтера.** Это единственная перемена, после
   которой лист стал читаться идеально. Умолчание `3*-d` (450 при `-d 150`)
   выбрано под общий случай и на лазернике 600 dpi работает против себя.
2. **Линейка — прибор для наводки.** Цель — измеренная ширина чуть ниже 100%.
   Ниже 95% — мало чернил, выше 110% — точки смыкаются.
3. **`-s` — вторичен**, и при `--image-dpi 600` у него всего четыре шага
   (50/75/75/100). `-s 75` при 600 dpi и есть найденная точка.
4. Ноль починок ECC на `75.bmp` значит, что на этой паре принтер+сканер есть
   запас: `-d 200` при `--image-dpi 600` даёт 3 px на ячейку и ~1.8x ёмкости,
   и по §8.2 у трёх пикселей на точку остаётся 1.75x запаса по размытию.

## 14. 18.09, ночь: `-d 200` на этом принтере невозможен, и почему `-r 0` — правильный ответ

### 14.1 Растекание — фиксированная величина, а не доля

`ScanImage50.bmp`, напечатан `-d 200 --image-dpi 600`, не читается **вообще** —
ни одного блока, метка страницы не найдена. Линейка объясняет почему:

| лист | ячейка в скане | нарисовано | линейка | измеренное растекание |
|---|---|---|---|---|
| `75.bmp`, `-d 150` | 3.94 px | 3 px = 76% | 96% | +0.83 px |
| `ScanImage50`, `-d 200` | 2.95 px | 2 px = 67% | **99%** | +0.95 px |

Растекание одинаковое — около **0.9 px при 600 dpi, то есть 0.04 мм**. Это
свойство пары принтер+стекло, и оно **абсолютное**, не пропорциональное. Значит
зазор, который нужно оставить, тоже абсолютный, и чем мельче ячейка, тем большую
её долю он съедает. При ячейке 3 px и точке 2 px зазор равен 1 px — растекание
съедает его целиком, точки смыкаются, модуляции нет, читать нечего.

При `-d 150` ячейка 4 px, зазор 1 px, растекание те же 0.9 — и лист читается
целиком без починок. Обрыв между 96% и 99%, то есть между «зазор 0.16 px» и
«зазора нет». Бритва.

### 14.2 Спасти `-d 200` на этой машине нечем

При ячейке 3 px округление `-s` даёт всего два варианта: `-s 50…83` → 2 px,
`-s 84…100` → 3 px. Меньшая точка уже использована. Один пиксель потребовал бы
`-s ≤ 49`, чего CLI не принимает (нижняя граница 50), да и 1 px при 600 dpi —
это 0.042 мм тонера, ниже того, что лазер укладывает повторяемо. Пробовать
можно, рекомендовать нельзя, границу молча опускать не стал.

Значит потолок этой пары — **`-d 150 --image-dpi 600`**, и ёмкость приходится
брать не плотностью, а избыточностью.

### 14.3 Поэтому `-r 0`

Блоков данных на листе A4 при `-d 150 --image-dpi 600`:

| | блоков | байт | к умолчанию |
|---|---|---|---|
| `-r 2` | 948 | 85 КБ | −20% |
| `-r 5` (умолчание) | 1180 | 106 КБ | — |
| `-r 10` | 1280 | 115 КБ | +8.5% |
| **`-r 0`** | **1422** | **128 КБ** | **+20.5%** |

### 14.4 Как сделана раскладка без групп

Формат менять не пришлось: адрес блока данных всегда несёт ноль в старшей
тетраде — там, где блок восстановления несёт размер своей группы. Поэтому
страница без блоков восстановления читается любым декодером, включая 1.20, и
`Finishpage` просто никогда не находит группу для починки (у него уже стоит
`if (pf->ngroup>0 …)`).

Изменилась только раскладка в `Printnextpage`: при `redundancy==0` нет строк,
которые надо возглавлять суперблоком, поэтому метки **разбросаны по листу**, а
данные занимают всё остальное. Метки четыре (`NSUPER`) — при `r>0` их
`redundancy+1` плюс все незанятые ячейки, и не зря: страница, у которой
единственная метка повреждена, теряется целиком. Это ровно то, что случилось с
`ScanImage50`. Четыре метки стоят 0.2% ячеек.

Проверено: стёртый угол с первой меткой не мешает странице назвать свой файл —
теряются только четыре затёртые ячейки.

`-r 1` отвергается: один блок восстановления на один блок данных — это вторая
копия листа, а не избыточность.

## 15. 18.09, ночь: умолчания — `-r 0` взято, `--header` отвергнут, и почему

Состояние на момент записи: `master` = `9aaa06c` (тег `v1.4`), в рабочем дереве
**не закоммичено** 17 строк — `src/main.c` и `test_cli.py`. Ветка
`quality-map-and-neighbour-resync` слита и удалена.

### 15.1 `-r 0` по умолчанию — сделано

`pb_redundancy=0` в `src/main.c:91`. Лист A4 при `-d 150 --image-dpi 600`
держит 1422 блока против 1180. Все проверки проходят.

Один тест пришлось привязать к `-r 5` явно: он меряет границу ёмкости
(«44100 байт ровно заполняют первый лист, а 16 байт выравнивания требуют
второго»), и такую границу нельзя оставлять на усмотрение умолчания.

### 15.2 `--header` по умолчанию — **отвергнут, и это находка**

Разреженный лист (4 КБ на A4, сетка в три ряда) с заголовком не читается, и
зависит это от геометрии бумаги:

| бумага | с заголовком | с `-n` |
|---|---|---|
| Letter | **No image** | 46/46 |
| A5 | **No grid** | 46/46 |
| A4, повёрнут на 180° | **No image** | 46/46 |
| A4 вертикально, A3, A6, Legal, Tabloid | 46/46 | 46/46 |

**Механизм.** `Getgridposition` ищет границы растра по профилю локального
контраста (`cmax-cmin` по пяти пикселям в точке) и берёт порог **50% от
максимума**. Края глифов контрастнее точек сетки, поэтому на разреженном листе
максимум задаёт текст, ряды сетки до половины не добирают, и границы
**схлопываются на текстовую полосу**. Дальше окно 1024×1024 садится в текст,
`cmax-cmin<1`, и лист отвергается целиком. Почему одна бумага проходит, а другая
нет, — вопрос того, куда попадает окно, то есть чистой геометрии.

Слабость не новая: `--header` мог это сделать всегда. Но как необязательный флаг
на плотном листе она почти не кусалась, а как умолчание кусается сразу.
Поэтому умолчание оставлено выключенным.

### 15.3 Побочно: `-n` и `--no-header` не работали никогда

`{"no-header",0,0,'n'}` стоит в таблице опций с самого начала порта, а
`case 'n':` был **пустым `break`**. То есть опция годами принималась и молча
игнорировалась. Теперь выключает заголовок — это единственное, что оставлено в
дереве из этой части работы, и проверяется функционально: Letter + `--header`
даёт «No image», Letter + `--header -n` даёт 46/46.

### 15.4 Косметика «SHA-256 под сеткой» — скорее всего это не косметика

Предложение перенести строку с дайджестом из нижнего поля прямо под блок точек
связано с §15.2 сильнее, чем кажется.

Сейчас текст стоит в отдельной полосе, отделённой от сетки белым зазором, и
границы растра **прыгают** на него целиком. Строка вплотную под сеткой окажется
внутри растра: границы не прыгнут, а расширятся на высоту строки — и окно,
центрированное на таких границах, почти наверняка останется на сетке. То есть
перенос может оказаться **функциональным исправлением**, а не косметикой. Но это
гипотеза, наугад ставить нельзя.

### 15.5 Порядок работ, когда вернёмся

1. **Порог в `Getgridposition`**: устойчивая оценка вместо 50% от максимума.
   После правки «привязка по всему листу» (§11) слишком широкие границы почти
   безвредны — профиль суммируется по всему растру и текст в нём разбавляется, —
   а схлопнутые смертельны. Это правка **первого шага каждого декодирования**,
   поэтому мерить по всему набору: 69 синтетических листов плюс реальные сканы.
2. Перенести строку SHA-256 под сетку — уже безопасно.
3. Только после этого включать `--header` по умолчанию.

Пока: печатать с `--header` на плотном листе (все реальные листы здесь плотные),
а на разреженном выключать через `-n`.

### 15.6 Как мерить, чтобы не обмануться

Три ловушки, каждая стоила времени именно в этой сессии — и все три давали
**самосогласованную, но неверную картину**:

- **Скрипт правки упал на середине и не записал ничего.** Правки применялись
  батчем с `assert` на каждый шаблон, запись — в конце. Один непопавший шаблон —
  и не применилось **ничего**, при том что справка (правленная отдельным
  прогоном) уже говорила новое. Полчаса ушло на измерение умолчаний, которых в
  бинарнике не было. Проверять факт правки в файле, а не в своём намерении.
- **Устаревший файл в измерении.** Цикл `--encode -o c.bmp` без `rm` перед ним:
  когда кодирование падало, декодировался **предыдущий** `c.bmp`, и таблица
  выглядела осмысленной. Удалять выход перед каждым прогоном и проверять код
  возврата.
- **Переиспользованный каталог тестов.** Диагностика шла по `page.bmp` из
  каталога, где лежал файл от предыдущего, ещё сломанного прогона. По размеру
  выяснилось, что это вообще Letter, а не A4, то есть падение было совсем в
  другом месте набора. Каталог под каждый прогон — чистый.

## 16. 19.09: перенос из копии проекта — взят минимальный набор

В копии `paperback-cli-master — копия` на `master` лежало семь коммитов поверх
`9aaa06c` и ветка `experiment/hash-barcode-markers`. Ветка не берётся: QR ест
ёмкость и не ложится в компоновку; область под сеткой узкая и длинная, так что
при возврате к машинной подписи смотреть надо на 1D, а не на квадрат.

Взято четыре вещи. Нумерация разделов ниже — по журналу копии.

### 16.1 Печать заголовка: серый текст и подвал под сеткой (копия, §16)

`src/Printer.c`: `Drawheadline` рисует уровнем 128 вместо 0, полоса подвала
начинается с `gridtop+height`, а не от нижнего поля листа. Обе правки
возвращают поведение оригинала 1.20, потерянное при портировании.

Механизм — из §15.2: порог поиска растра берётся как половина максимума
профиля локального контраста. Края чёрных глифов контрастнее точек, поэтому
на разреженном листе максимум задаёт текст, а границы схлопываются на текстовую
полосу. Серый текст убирает превосходство глифов, подвал вплотную к сетке
убирает пустую полосу, на которой центрировалось окно поиска.

Измерение воспроизведено здесь заново, не перенесено из копии: 4096 байт
(`bytes(range(256))*16`), `--dpi 100 --header`, семь форматов × 0°/180°,
успех — код 0 и побайтовое совпадение.

| сборка | восстановлений |
|---|---|
| текущий `src/Printer.c` до правки | 9/14 (падали A4 180°, Letter 0°, A5 0° и 180°, Legal 180°) |
| после правки | 14/14 |

Содержание строк не менялось: сверху имя, время, размер и номер страницы,
снизу SHA-256 и рекомендация по сканированию. Умолчание `--header` остаётся
выключенным. Старые отпечатки с чёрным текстом это не чинит.

### 16.2 Проверка структуры адреса до фиксации ориентации (копия, §21–22)

`src/Decoder.c`, `Recognizebits`: после RS и CRC, но **до** присвоения
`pdata->orientation` и `lastgood` проверяется, что адрес вообще пригоден для
сборщика — группа 0..`NGROUPMAX`, смещение меньше `MAXSIZE`, адрес кратен
размеру группы × `NDATA`. `SUPERBLOCK` пропускается как есть, группа 1
оставлена для старых страниц.

Основание — не гипотеза: на реальных сканах `01.bmp` принимал единственный блок
со стираниями с адресом группы 12, `ScanImage50.bmp` — два, группы 15 и 12, при
`NGROUPMAX=10`. Стирания тратят всю избыточность RS, после чего от подделки
защищает только 16-битный CRC; такой ложный приём задавал ориентацию всей
страницы и считался прочитанным блоком. Прежнее утверждение §12.3 «адрес всегда
правдоподобен» этим опровергнуто.

### 16.3 Не повторять тот же проход без прочитанных блоков (копия, §23–24)

`Decodenextblock` начинает второй проход только при `orientation>=0`. Пока
ориентация неизвестна, ни один результат не принят: нет ни новой ориентации, ни
соседей для `Predictorigin`, ни изменения `lastgood`, — второй просмотр той же
сетки даёт тех же кандидатов. В копии это дало `ScanImage50.bmp` 111,79 → 56,27 с
при прежнем отказе; здесь время не перемерялось, сканов в дереве сейчас нет.
